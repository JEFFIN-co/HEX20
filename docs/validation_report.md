# HEX20 Milestone 10 — Final Validation & Security Stress Campaign

## Objective

Milestone 10 performs a deterministic 1,000-command validation campaign against the actual HEX20 secured end-to-end uplink processor developed in Milestones 1–9.

The campaign exercises normal command routing, noisy uplink reception, frame CRC rejection, authentication failure, authenticated header manipulation, unknown authenticated commands, malformed security envelopes, malformed packets, and replay attempts.

## Pipeline under test

```text
Noisy uplink
    ↓
Frame synchronization
    ↓
Transfer-frame decoding + CRC validation
    ↓
Space-packet decoding
    ↓
Security envelope parsing
    ↓
HMAC authentication + freshness/replay check
    ↓
Authenticated command ↔ APID/service/subtype validation
    ↓
APID/PUS routing
    ↓
Handler execution + telemetry counters
```

## Expected acceptance model

The five benign scenario groups total 680 commands and are expected to be accepted. The six attack/fault groups plus malformed packet group total 320 commands and are expected to be rejected.

## Results

The machine-readable result files are generated by `hex20_m10_final_validation_runner.py`:

- `hex20_m10_validation_results.json`
- `hex20_m10_validation_results.csv`

Run the campaign locally to obtain the timing values for the current machine. Timing is a prototype measurement, not flight qualification.

## Security observations

1. CRC corruption is rejected before the command reaches the security/routing path.
2. Authentication-tag tampering is rejected by the security gate.
3. A valid authenticated command with a manipulated packet header is rejected because the authenticated command does not match the APID/service/subtype tuple.
4. Unknown authenticated command codes are rejected instead of being routed.
5. Malformed security envelopes do not reach command handlers.
6. Reusing a previously accepted authenticated frame is rejected by the freshness/replay guard.
7. Noise surrounding a valid frame can be synchronized and processed by the existing frame synchronizer.

## Limitations

This is a software prototype. It does not establish flight readiness, cryptographic certification, radiation tolerance, deterministic hardware timing, formal CCSDS/PUS compliance, key-management correctness, or resistance to all possible fault-injection and cyber-physical attack classes.

The current demonstration secret is a development/demo value and must not be reused for a real spacecraft.

## Recommended next engineering steps

- Replace the demonstration security construction with a mission-approved cryptographic design and key-management process.
- Validate exact CCSDS transfer-frame and PUS profiles required by the target mission.
- Add hardware-in-the-loop timing and fault-injection testing.
- Add persistent/non-volatile replay-counter handling and rollover policy.
- Expand APID/service/subtype configuration and handler coverage.
- Add traceable requirements and verification IDs for each protocol/security requirement.
- Package the final dashboard and validation artifacts for the HEX20 demonstration.
